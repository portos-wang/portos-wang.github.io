Build and maintenance

Checks, entry updates in isolated worktrees, packaging and local synchronisation.

The maintenance command is how bundled components move: Pi SDK and the UI layer, the built-in Skill Packs and Plugins, and the external MCP service definitions. It never edits your working branch directly. Candidates are prepared in a separate Git worktree, verified there, and only then packaged or synced.

The loop

Without --no-verify, update continues straight into installing and verifying. Stable releases are preferred; when a Git project has no stable tag, the report says so explicitly and pins the actual commit.

Reading the status

Status Meaning
prepared The candidate exists but has not passed verification.
verified The candidate passed every check in its manifest.
blocked / conflict A source, an old baseline or a merge conflict needs a decision. Reports and conflict files are kept.
verification-failed Some checks failed; read the report and the adjacent commands.log.

Every command prints the candidate directory, branch, Run ID and report path. Reports live under ohpie-maintenance/runs/<Run-ID>/ inside the Git common directory. Your original checkout keeps its branch, index and uncommitted changes.

Scoped updates

The eight Pi SDK packages (pi-agent-core, pi-ai, pi-codemode, pi-coding-agent, pi-mcp, pi-schema, pi-telemetry, pi-tui) move to the same exact version. Skills and Plugins are merged from the real previous upstream, the new upstream and the current OhPie content, so local adaptations survive. A missing source or old baseline is reported as a blocker rather than silently ignored; pass --baseline-ref once you have identified the old commit, or --ref to pin a target commit or tag.

Packaging and local sync

Review the candidate diff first, then choose one or both:

package builds only inside the candidate directory and delivers the portable folder and installer into the original checkout's dist/, keeping earlier output. sync-local updates the installed Skills and Plugins while preserving configuration and keys; MCP environments are still installed explicitly by the Windows installer.

Further edits to the candidate invalidate the previous verification — run verify again before packaging.

Baselines and conflicts

Local sync prefers the baseline recorded at install time in ~/.ohpie/agent/.ohpie-builtin-baselines/, then records the new one. LF/CRLF differences are not treated as user edits; binary content is still compared byte for byte.

When an old installation has no recorded baseline, the candidate snapshot is adopted only if the content matches it exactly. Otherwise the command returns needs-baseline — the new fixes must not be mistaken for a common ancestor of an older install. Overlapping local edits produce a conflict and keep the three-way files; nothing is force-overwritten.
