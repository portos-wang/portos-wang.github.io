Release and updates

From the version bump to the public update manifest — the five places one Windows release touches.

OhPie is released locally: build here, verify here, upload the installer by hand, update the public manifest by hand. The repository still contains .github/workflows/release.yml, but it is kept as reference only — until Actions billing is restored, a tag-triggered build fails.

Five places one release touches

Place What changes Who reads it
package.json / package-lock.json The version The build, and resources/app/package.json
Git tag vX.Y.Z Marks the release commit You, and the GitHub Release
docs/releases/vX.Y.Z.md The human-readable notes Users, the update page
GitHub Release Installer, checksum, blockmap Everyone who downloads
docs/releases/site/latest.json + public Pages The only source the app polls Every installed OhPie

Miss one and you get either "released but invisible" or "update offered, download 404".

Before you start

  1. Working tree clean, HEAD equal to origin/main, containing only this release's changes.
  2. Package from a separate worktree — never from the checkout serving development.
  3. Every check below passes, and the target tag is still free.
  4. Write docs/releases/vX.Y.Z.md in the same shape as the previous release: main changes / runtime and compatibility / download and verification / upstream baseline.

The five steps

1. Set the version

Neither step creates a Git tag. The tag belongs on the release commit that includes the notes, not before it.

2. Commit, tag, push

Push the named tag. Do not use git push --tags: this checkout may also hold upstream tags.

3. Build

Output lands in dist/: OhPie Setup X.Y.Z.exe, the portable win-unpacked/ folder, and .blockmap.

After building, confirm two things: the installer name carries the right version, and dist/win-unpacked/resources/app/package.json reports the same version.

4. Verify and upload

--generate-notes produces a commit summary. It does not replace the human-written docs/releases/vX.Y.Z.md.

5. Publish the public manifest

Commit and push in portos-wang.github.io; Pages deploys automatically. The manifest lives at:

index.html (the release-notes page) only needs updating when its layout changes; its content is rendered from latest.json.

Hard requirements for the build

  • Never run next build while a dev server is running: both write .next/ and corrupt each other.
  • Use a separate worktree with a private build profile and a hard-linked dependency copy. Turbopack rejects a dependency junction that points outside the worktree.
  • Run the smoke test against the artefact, not the source tree:

It checks startup, product identity, port collision, relocation and clean shutdown.

How the app finds the update

  • An installed OhPie polls the manifest every 12 hours, with a 5-second timeout.
  • When the manifest version is newer, the version line on the new-session page shows → vX.Y.Z ↗, linking to the matching anchor on the release-notes page.
  • A missing or unreachable manifest is skipped silently — no error dialog, and no stale notice.

When things go wrong

Situation Action
Build fails Confirm you are not in the dev checkout; confirm the dependency copy is a hard link, not a junction
Wrong asset uploaded Delete that asset and upload again; do not recreate the tag
Notes are wrong Fix docs/releases/vX.Y.Z.md and latest.json, commit again; leave the installer alone
Shipped with a serious defect Release X.Y.Z+1; do not overwrite the installer or move the tag
Manifest points at the wrong version Correct latest.json and push; the app recovers on its next poll

Published tags and installers are immutable. Fix forward with a new version — otherwise checksums and the files users already hold stop matching.

Release checklist

  • package.json and package-lock.json agree
  • The tag sits on the commit that includes the notes
  • Typecheck, lint and tests pass, with results recorded
  • Build ran in a separate worktree
  • Installer name and resources/app/package.json version agree
  • .sha256 and .blockmap uploaded alongside the installer
  • docs/releases/vX.Y.Z.md committed
  • latest.json has the new version, date, notes, with history preserved
  • Public repository pushed; the manifest URL returns 200
  • An older install sees the update notice and the link opens

Do not

  • Do not use npm run release — that is the upstream npm publishing script, not OhPie's Windows entry point.
  • Do not git push --tags — it drags upstream tags along.
  • Do not npm run build inside the development checkout.
  • Do not put unredacted logs, absolute local paths or private service addresses into release notes.
