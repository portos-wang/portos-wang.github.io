构建与维护

检查、在独立 worktree 中准备候选、验证、打包与同步本机。

维护命令负责内置组件的更新：Pi SDK 与界面层、内置技能包与插件、外部 MCP 服务定义。它从不直接改动你当前的分支——候选在独立的 Git worktree 里准备、验证，之后才被打包或同步。

工作循环

不加 --no-verify 时，update 会直接继续安装与验证。默认选稳定版；Git 项目没有稳定标签时，报告会明确写出这一点，并固定实际提交。

看懂状态

状态 含义
prepared 候选已就绪，但尚未通过验证。
verified 候选通过了清单中的全部检查。
blocked / conflict 来源、旧版本基线或合并冲突需要处理；报告与冲突文件都会保留。
verification-failed 部分检查未通过；查看报告与旁边的 commands.log。

每条命令都会打印候选目录、分支、Run ID 与报告位置。报告位于 Git 公共目录下的 ohpie-maintenance/runs/<Run-ID>/。原检出目录保留自己的分支、索引与未提交改动。

限定更新范围

Pi SDK 的八个包（pi-agent-core、pi-ai、pi-codemode、pi-coding-agent、pi-mcp、pi-schema、pi-telemetry、pi-tui）使用同一个精确版本。技能与插件按真实的旧版上游、新版上游和 OhPie 当前内容三方合并，因此本地适配能保留下来。缺少来源或旧版本基线会被报告为阻断项，不能靠检查绕过；确认旧版提交后可传 --baseline-ref，或传 --ref 固定目标提交或标签。

打包与本机同步

先在候选目录查看差异，再选择一项或两项：

package 只在候选目录构建，成功后把便携目录与安装器交付到原仓库的 dist/，保留之前的输出。sync-local 更新本机已装的技能与插件，保留配置与密钥；MCP 环境仍由 Windows 安装器显式安装。

继续修改候选内容会让上一次验证失效——打包前重新跑 verify。

基线与冲突

本机同步优先使用安装时记录的基线（~/.ohpie/agent/.ohpie-builtin-baselines/），成功后再记录新基线。LF/CRLF 差异不会被当成用户改动，二进制内容仍按字节比较。

旧安装没有记录基线时，只有内容与候选起始快照完全一致才会采用它；否则命令返回 needs-baseline——不能把候选里的新修复误当成旧安装的共同祖先。重叠的本地改动会返回冲突并保留三方文件，不会强制覆盖。

测试的导入约定

导入的模块若存在不带扩展名的相对引用，测试必须通过 jiti 桥接，因为 Node 原生 ESM 解析器不接受这种写法：

全部使用显式扩展名的模块可以直接导入。这样 Node 原生 node --test 就能直接跑 TypeScript 源码。

维护操作永远不会把候选合并回你的分支。确认满意后，先处理原有的未提交工作，再按正常 Git 流程合并候选分支。
